## 附带发现：`test/background.test.mjs` 有低频偶发失败（已加固）

- 现象：全量跑时 `not ok 1 - Bash run_in_background`，**约 1/7 概率**；
  单独跑该文件 **4/4 通过**；随后连跑 6 次全量 **6/6 通过**（不可稳定复现）。
- 判定：**调度延迟，不是产品缺陷** —— 断言同时要求 `done` 与输出内容，
  真挂死仍会失败；失败点更可能是 `node --test` 并行 13 个文件时
  `cmd.exe` 起进程 + `close` 事件的延迟超过原来的 **5 秒**轮询预算。
- 处理：轮询预算 5s → **20s**（50×100ms → 200×100ms），并写明理由。
- **注意**：这是本轮唯一的测试改动，属"为了让 CI 不随机变红"，不是放宽断言。

## 修掉一个 CSRF：`/api/update` 曾是 GET 且回环下免鉴权

**发现过程**：做覆盖率审计 → 查"门控开关在测试里出现过几次" → 补了 egress 测试 →
顺手审 `static.mjs` 的路由 → 发现更新接口的问题。

**问题**：`/api/update` 是**有副作用**的接口（下载更新包 → 覆盖安装目录 → `relaunch()`
里 `process.exit(0)` 重启），但它：
1. 走 **GET**（`static.mjs` 原先只允许 GET/HEAD，它就落在 GET 里）；
2. 在回环绑定下 `httpGate()` 直接 `{ok:true}` —— **不需要任何凭据**。

→ 任意网页只要 `<img src="http://127.0.0.1:8788/api/update">` 就能逼用户
下载更新并重启服务。跨站发 GET 不需要 CORS 授权，副作用照样发生。
（危害有限：更新源是用户自己配的 `LIMKENION_UPDATE_URL`，攻击者不能换源；
但能强制下载 448MB + 打断正在跑的回合。）

**修法**（三处）：
- `server/static.mjs`：
  - 方法检查加例外（放行 POST `/api/update`）+ **显式要求** POST（GET/HEAD 一律 405）
  - 两个更新接口都要求 `x-limkenion-token` 头 === `WS_TOKEN`，否则 403 ——
    跨站页面**设不了自定义头**（会触发 CORS 预检，而本服务不下发任何 CORS 头），
    所以这条天然免疫 CSRF
  - 踩坑：`urlPath` 的声明在方法检查**之后**，我先把检查挪前面造成了 TDZ 引用；
    已把 `decodeURIComponent` 整段上移。**注意比较的是未归一化的 urlPath**，
    `/api\update` 走不到例外 → 落到 405，是失败关闭方向。
- `src/api.ts`：把 token 解析抽成导出的 `resolveWsToken()`（WS 握手与更新接口共用）
- `src/App.tsx`：`/api/update` 改 POST，两个接口都带 token 头

**回归防线**：新增 `web/test/updateEndpoints.test.mjs`（4 组 10 项）——进程内起 HTTP 服务

## 修掉一个"一条畸形消息打挂整个服务"（比 CSRF 更严重）

**发现**：从 CSRF 往外推一层 —— 审 WS 入口面（21 种消息类型）。
`server/protocol.mjs` 的 `ws.on('message')` 里是：

```js
void handleClientMessage(ws, msg, registry)   // ← 没有 .catch()
```

`handleClientMessage` 是 **async**，抛异常就是**未处理的 promise rejection** ——
Node 15+ 默认**直接终止进程**。

**实测复现**（写了 `.workbuddy-ai/i18n/_ws_fuzz_probe.mjs`：起真服务 + 连 WS + 灌 20 条畸形消息）：

```
服务进程退出码: 1 （死了！）
死在哪个用例: command 是对象
TypeError: Cannot convert object to primitive value
```

最小触发载荷：`{"type":"run_command","sessionId":"<有效>","command":{"toString":null}}`
—— 处理器里写的 `String(msg.command ?? '')` 本身就会抛（`JSON.parse` 出的对象
自带 `toString:null` 属性，遮蔽了原型链上的，`String()` 于是无法转成原始值）。
**注意：处理器里大量用 `String(x ?? '')` 兜底，靠读代码看不出问题，必须实测。**

**危害**：任何能过握手鉴权的客户端，一条帧就能让服务退出；
更糟的是**任何命令处理器里的 bug 都会变成整个服务下线**，而不是单条消息失败。

**修法**：`void handleClientMessage(...).catch(err => { console.error(...); send(ws,{type:'error',...}) })`
—— 单条消息失败即可，并把原因回给客户端。
坑：**别在 catch 里对 msg 做强制转换**，那可能正是刚才抛错的原因，会二次抛出。

**回归防线**：`test/protocol.test.mjs` 新增 describe「畸形消息不能打挂服务」（3 项）：
单条畸形回 error 且服务仍能应答 `get_models`、连灌 13 条畸形后仍可用、非 JSON 帧被静默丢弃。
**并且验证了测试确实能抓到回归**：`git stash` 撤掉修复 → 3 项全红（`pass 0 / fail 3`）；
恢复 → 全绿。（测试能过 ≠ 测试能抓回归，这一步不能省。）

测试数 **378 → 381**。

## 广播/单发韧性：一个死客户端不能拖垮其他客户端

接 crashGuard 之后查 WS 连接生命周期。bus.mjs 的 send() 里 `ws.send(JSON.stringify(msg))`
原先没 try/catch：一个「readyState 检查通过、但 send 时 socket 已死」的客户端（检查与
发送之间的竞态）会同步抛错，打断 broadcast 的整个 for 循环 → 其余客户端收不到这条消息，
异常还冒进调用方（runTurn 的 emit → broadcast）。全服务唯一的 ws.send 就在 bus 里，
所以硬化 send 一处覆盖全部 28 个广播点。

**修法**：
- send()：ws.send 包 try/catch，失败时把该客户端从注册表移除（已不可用，避免每次广播
  都抛、还打断别人），返回 false。
- broadcast()：再兜一层，单客户端失败 / build() 抛错不影响其他客户端。

**回归防线**：test/bus.test.mjs（死客户端不能打断广播且被移出；send 对 null / 未 OPEN /
发送抛错 都安全返回 false）。用真实 close 处理器清理，不污染其他测试。

## HTTP 静态层（static.mjs）审计：输入面已扎实，补顶层 try/catch

接 bus 之后查 HTTP 静态层。逐项核对畸形输入面，**其实已被各分支妥善处理**：

反斜杠/控制符等）**都不抛**（WHATWG 解析器宽容）——所以「外部畸形输入打挂服务」
